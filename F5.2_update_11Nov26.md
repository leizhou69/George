## Part B — found, not changed (for review)

Ordered by how much they matter.

### B1. Opus 5.5 runs cannot work as things stand — do not resubmit yet

All four attempts with real API traffic (2026-10-31 18:34 and 2026-11-01 22:16,
5UTR and CDS) show the same pattern in the SLURM logs: **every** model response
fails the fork's tag parse ("parsing error…", 30–115 times in a row, starting
with the very first call), and after ~1–1.5 minutes the API returns
`403 model_access_suspended` for the organisation for about six hours.

Two separate problems in `../biomni-fork/biomni/agent/a1.py::generate`:

1. **The response is being parsed as empty.** The content normaliser keeps only
   `text` / `output_text` / `redacted_text` blocks. The logs do not print the raw
   response, so the cause is unconfirmed — the model may be returning a block
   type the fork drops, or declining the request. One direct call that prints
   `stop_reason` and the raw content blocks would settle it; I did not make it
   because the suspension pattern suggests repeated calls are what trip the 403.
2. **The "repeated parsing errors" breaker is dead code.** It counts `AIMessage`s
   containing `"There are no tags"`, but the correction is appended as a
   `HumanMessage` whose text is `"But there are no tags"` (lower-case t). The
   count is always 0, so the loop retries until the recursion limit (500) or an
   API error. A fix needs to count *consecutive* failures: the successful s5
   5'UTR run had 20 non-consecutive parse errors and recovered, so a cumulative
   threshold of 2 would have killed it.

The 403 itself is an account-level matter and may need Anthropic support.
Whether the retry storm causes the suspension is an inference from timing, not
something the logs prove.

### B2. Held-out 5'UTR keys are labelled in tracked, pushed files

They are in `origin/main` history since commit `a72bfcd`. The CDS keys are not

### B14. The "masked" catalogs still mark every known disease locus (found 2026-11-11, from the Fable 5.2 and Gemini runs)

The catalog `Source` column has the value `KnownDiseaseAssociatedLoci` for the
given pathogenic loci **and for every withheld key**:

| Catalog | Rows with that `Source` | Given | Withheld keys | Other |
|---|---|---|---|---|
| CDS (`B_Cat_CDS_msk_TNR.tsv`) | 31 | 28 | 3 of 3 | 0 |
| 5'UTR GCN (`B_Cat_5UTR_GCNs_masked.tsv`) | 17 | 7 | 2 of 2 | 8 |
| 5'UTR TNR (in the ag_db `variants` dim) | 18 | 7 | 2 of 2 | 9 |

So in CDS, "`Source` says known disease but the locus is not in the given list"
identifies exactly the withheld keys. The column is in the registered catalog
files and in the ag_db `variants` view, which contradicts the "no pathogenic
labels in the DB" statements in `db/` and the schema text shown to the agent.

What the November runs did with it (from their logs):
- **Fable 5.2 (both regions)** flagged it as a label leak, excluded `Source` from
  modelling, and set those loci aside as a held-out check — i.e. it removes the
  withheld keys from its candidate list on purpose. Its 0/2 on 5'UTR reflects
  that, not a failure to rank them; expect 0/3 on CDS for the same reason.
- **Gemini 4 Carbon (CDS)** also spotted it, and additionally noted that the
  degenerate `CNG` canonical motif occurs almost only on curated disease loci
  (10 of 11 rows) — a second marker.
- The logs of the earlier runs (s5, o4.8, o5, o5.5) never print the label. That
  does not prove they did not use `Source` or the motif coding as a feature; the
  o5 CDS model's dominant coefficient is a motif-class flag that includes `CNG`.

Consequence: withheld-key recovery is not a clean metric until the catalogs are
re-masked (`Source`, and curated-only motif/boundary conventions) and the ag_db
`variants` dim is rebuilt or the column dropped. Runs that honour the leak score
worse than runs that ignore or exploit it.
